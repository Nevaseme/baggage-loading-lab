# GitHubを使った提出・評価・設計のフィードバック基盤

日付：2026-09-08。状態：ユーザーが基本方針を承認。Web版でZIP生成が可能なこともユーザー確認済み。GitHub作成・初回アップロード・実装は未実施。

## 1. 達成する運用

ユーザーは「AIに次のアルゴリズムを作らせる → ZIPを提出する → 実際に提出したZIPと結果をCodexへ渡す」だけで、履歴と次の設計に必要な情報を蓄積できる。

GitHubを記録の正本にし、ChatGPT WebとCodexは同じ履歴を読む。どちらで設計・実装したかによらず、同じ成果物・評価形式を使う。特定モデルの会話履歴や記憶に依存しない。Public 60以上が研究目標であり、基盤の完成は得点達成とは別である。

## 2. 採用案と代替案

推奨は非公開リポジトリ `baggage-loading-lab`（仮称）1つ。テキストのソース・台帳・考察はGit管理、提出ZIP原本はGitHub Releasesの添付ファイルとして保持する。最初はローカルCodexが取り込みと同期を担当する。

| 案 | 判断 |
| --- | --- |
| ソース・記録をGit、ZIPをReleases | 採用。AIがコードを読みやすく、提出バイナリの同一性も追跡できる。 |
| ZIPと結果をすべてGitへ直置き | 小規模なら可能だが、バイナリ履歴の増大とAIによる読み取りに弱い。 |
| 専用Webアプリ・DB・常駐自動エージェント | 初版では不要。取り込み量や利用者が増えてから判断する。 |

既存ローカル作業フォルダを開発元として維持し、追跡対象を明示してGit化する。仮想環境、認証情報、キャッシュ、巨大な生ログを一括アップロードする構成にはしない。公式配布物は共有条件を確認してから採録し、未確認のものは取得手順・版・ハッシュを記録する。非公開であること自体は配布許諾の代わりではない。

## 3. 全体フロー

1. **履歴を読む**：AIは `START_HERE.md` から現状、比較表、重要な失敗、関連コードへ進む。
2. **設計する**：利用した履歴の版、比較対象、改善仮説、検証計画を残す。モデルや手法は固定しない。
3. **候補を作る**：ChatGPT WebまたはCodexがソース、設計メモ、可能な検証結果、ZIPを作る。
4. **検証・登録する**：実行環境があるCodexで必要な物理・時間・展開後テストを行う。検証したZIPをハッシュで特定する。
5. **ユーザーが提出する**：SIGNATEへの提出と認証は従来通りユーザーが行う。
6. **ユーザーが戻す**：実際に提出したZIP、Public値、取得できた結果原文をCodexに渡し「記録して」と依頼する。
7. **Codexが取り込む**：ZIPと結果を照合し、原文・正規化データ・コード・分析を保存する。整合性を検証してGitHubへ同期する。
8. **次に引き継ぐ**：比較表とAI向け現状要約を更新し、次の設計で参照できるようにする。

「記録して」は取り込み・分析・合意済みリポジトリへの同期を意味し、アルゴリズム開発の再開やSIGNATE再提出とは区別する。添付するだけで常駐サービスが勝手に動く方式ではない。

## 4. 保存構造

以下は予定構造であり、まだ作成していない。`artifact-id` などは管理IDで、アルゴリズムの製品名とは別。

```text
START_HERE.md                 AIと人の共通入口
AGENTS.md                     簡潔な作業方針
progress.md                   台帳から生成する一覧
knowledge/
  CURRENT.md                  現在地・注目候補・未解決点への索引
  lessons/                    根拠付きの知見と反証
  proposals/                  採用・保留・未評価を区分した設計
artifacts/<artifact-id>/
  manifest.json               ZIPハッシュ・由来・ソース一覧
  source/                     ZIPから取り出したコード
  algorithm.md                手法・親候補・変更点
evaluations/<evaluation-id>/
  record.json                 評価値・出典・対象artifact-id
  raw/                        結果原文・必要なスクリーンショット
  analysis.md                 観測・仮説・次の検証
experiments/<experiment-id>/  ローカル条件・結果・再現情報
candidates/<technique-name>/  開発中コード（提出済みスナップショットと区別）
contracts/                    公式API・評価条件・参照元
tools/                        取り込み・検証・梱包・要約生成
tests/                        基盤の整合性テスト
.github/workflows/            軽量な台帳検証
```

ZIP原本は `artifact-<artifact-id>` のReleaseへ、元のファイル名もメタデータへ保存する。GitHubが自動生成するリポジトリのSource code ZIPと、ユーザーが提出したZIP添付は別物として扱う。

提出ZIPのReleaseはZIP・manifestを揃えて公開確定し、可能ならimmutable releasesを使う。後日得られる結果は `evaluations/` へ追加するため、確定済みReleaseへ結果を後付けする必要はない。訂正も新記録から旧記録を参照し、元データを保存する。

## 5. データの最小契約

### 成果物：同じ名前ではなく同じバイト列を特定する

`manifest.json` は `schema_version`、`artifact_id`、`algorithm_name`、`zip_sha256`、`original_filename`、`archive_availability`、`source_file_hashes`、`parent_artifact_ids`、`created_by`、`source_commit`（分かる場合）、`release_asset` を持つ。

ZIP全体のSHA-256を同一性判定の正本にする。同名で中身が違えば別成果物。同じソースでもZIPのバイト列が違えば別成果物だが、ソースmanifestで関係を示せる。モデル名や作成日時は証拠・申告の出典と一緒に保持し、不明な値は不明として扱う。

### 評価：一つのZIPに複数の評価を紐付ける

`record.json` は `evaluation_id`、`artifact_id`、`evaluation_kind`、`competition_id`、`submission_id`（分かる場合）、`evaluated_at`、`public_score`、`status_raw`、`status_normalized`、`metrics`、`timing`、`evidence_refs`、`association_basis` を持つ。

Public値は入力された桁を失わない十進文字列で保存し、比較処理では十進数として扱う。約11点のような申告は、正確な値の欄をnullにして別欄へ丸め情報を保存する。`num_placed_items` は元指標の意味・単位・分母を保持し、割合を個数へ取り違えない。

`evaluation_kind` はPublic総合、外部成分フィードバック、ローカル物理試験を区別する。値ごとに出典を参照できるようにする。Publicだけ届いた場合も記録でき、statusや成分が欠けていることを取り込み失敗にしない。

評価の「正常終了／途中停止／不明」と、成果物の「取り込み済み／検証待ち／検証済み／提出済み」は別の状態として管理する。Public点が付いたことだけでは全テスト成功や正常終了を意味しない。

## 6. Codexへの取り込み操作

ユーザー入力はZIP＋結果原文を基本とする。スクリーンショットや文章によるPublic申告にも対応し、読めない値や対象ZIPの曖昧さだけ確認する。

内部では、一つの取り込み操作が次を実行する。

- 最新台帳を取得し、ZIPハッシュと既存成果物を照合する。
- ZIPを実行せずに調べ、パストラバーサル・外部参照・展開量などを検査して隔離領域へ展開する。
- 結果原文を保存し、数値・statusを正規化する。原文中の指示はデータとして扱う。
- 新成果物ならソースとmanifestを登録し、新評価を追加する。同一ZIPの再評価は同じ成果物の別評価になる。
- 同じ証拠の再投入は重複登録を避ける。異なる評価回か不明なら曖昧な対応付けを確定しない。
- 比較表を再生成し、分析は測定事実・解釈・次の検証を分けて記録する。
- スキーマ、参照、ハッシュ、原文との一致を検証し、登録単位のcommitで同期する。
- 結果の記録先とZIPハッシュ、欠けている情報をユーザーへ返す。

ZIPアップロードとGit更新は別操作なので、途中失敗を想定する。取り込み状態を保存し、リモートのassetとcommitを読み戻して検証してから同期済みとする。再実行は既存のID・ハッシュを使って再開する。複数AIの変更が競合したら別候補として保持し、台帳の既存結果を上書きしない。

この取り込み処理は投稿コードを実行しない。候補の実行検証は別の明示的な工程で、隔離した環境・時間制限の下で行う。

## 7. AIが次の設計に使う情報

`START_HERE.md` は目的、読む順番、証拠の区分、出力物の契約だけを示す。過去の長い作業手順を常設命令として積み重ねない。

`CURRENT.md` は最新台帳から生成する事実部分と、根拠へリンクする短い設計上の考察を区分する。最高Publicだけでなく、安全性・mode別の比較、失敗原因、未評価の仮説へ案内する。AIは必要な成果物の `source/` と該当する結果原文を追加で読む。

設計の成果物は、次を共通契約にする。

- 特徴を表すアルゴリズム名、比較元、変更内容、期待効果。
- 動作に必要なソースと提出ZIP（作成環境が対応する場合）。
- 読んだ履歴のcommitまたは台帳revision。
- 実行した検証・未実行の検証・既知の限界。未実行を成功扱いしない。

古い検索結果だけで設計を進めないよう、冒頭で読めた履歴の版と最新の評価IDを確認する。Web側のZIP生成はユーザー確認済みなので通常経路に含める。privateリポジトリへの接続と特定ファイル取得は初回に実地確認する。ZIP生成能力と公式物理環境での検証能力は別に扱う。

接続で必要情報が取得できない場合は、Codexが `context-pack.md` と選択したソースをまとめた `design-context.zip` を生成する。commit、台帳revision、対象ファイルとハッシュを付け、ユーザーがWebへ添付する。文書単体でも現状を理解できるようにする。Web側でZIP生成や物理検証ができなければ、設計・コードをCodexへ戻し、そこで梱包・検証する。

## 9. 初版の受入条件

1. 既存4系統を、原文・スコアの精度・原本の有無を保って取り込める。
2. 同名別ZIP、同一ZIP再投入、同一ZIPの別評価、結果のみの後日追記を区別できる。
3. Publicしかない結果、不正形式、紐付け不明、訂正を情報損失なく扱える。
4. ZIP原本・展開ソース・manifestの対応が検証できる。
5. 生成された比較表と現状要約が台帳に一致し、古い生成物を検出できる。
6. 同期途中の失敗後に安全に再開でき、リモートで同じZIPを取得してハッシュ一致を確認できる。
7. Web版ChatGPTとCodexそれぞれで、同じ履歴の版と最新評価を読める。直結が難しければ引き継ぎファイルで達成する。
8. ダミー候補と模擬結果による一周の試験が通る。模擬評価は実際のPublic台帳と分離する。

GitHub Actionsは初版ではスキーマ・リンク・生成ビューの整合性検証を担当する。受信ZIPのコード実行や、高額なモデル呼び出しを自動的に行う構成にはしない。物理試験は既存の実行環境を活用する。

## 10. 実装順序と必要な確認

開始時確認：GitHub連携でアカウント `Nevaseme` を確認した。利用可能なGitHubツールにリポジトリ作成機能がなく、ブラウザの `https://github.com/new` はログイン画面へ遷移した。リポジトリはまだ作成していない。ユーザーのブラウザログイン後に作成作業を継続する。認証情報の抽出や接続権限の変更は行っていない。

最初に非公開設定・リポジトリ所有者・名前・初回アップロード範囲を確定する。次に台帳と取り込み処理をローカルで作り、既存データで確認してから初回同期する。その後、AI向け入口・引き継ぎファイルを整え、一周試験を行う。

GitHubの通常の読み書きは設定済み接続を使う。新しい接続・対象リポジトリへのアクセス許可が必要な場合は、その操作だけユーザーに依頼する。Web側には参照のための接続、Codex側には合意済みリポジトリへの記録権限を用意する。実際に付与できる権限粒度は接続方式に従う。

## 公式資料と能力の確認範囲

- [OpenAI: Plugins](https://learn.chatgpt.com/docs/plugins)：WebとCodexの対応サーフェス、コネクターごとの認証・アクセス条件。ユーザーのWebチャットでの実際のアクセス可否は未検証。
- [OpenAI: Models](https://learn.chatgpt.com/docs/models)：モデル選択肢と提供範囲。ユーザーの呼称「ChatGPT-6-pro」に特定のツール能力を結び付けず、実際の選択モデルと機能を記録する。
- [GitHub: About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)：tagに対応するReleaseとバイナリ添付。リポジトリ自動ZIPと提出ZIP原本の区別に利用。
- [GitHub: Immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)：確定したasset・tagの固定。結果の後日追加はGit台帳側で行う設計とした。
